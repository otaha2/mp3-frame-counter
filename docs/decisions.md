# Decisions

Every technical choice gets a row: what was decided, what else was considered,
why, and where the evidence lives.

| #   | Decision                                                                                                                                                             | Alternatives considered                                                                                                                                      | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Evidence                                                                                     |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| D1  | `frameCount` = physical frames **minus** the Xing/Info/VBRI metadata frame when one is present (sample → 6089).                                                      | (a) Count every physical sync-framed unit (sample → 6090). (b) Trust the Xing header's own frame-count field without walking.                                | mediainfo, `ffprobe -count_frames` and the file's own Xing field all report 6089: the metadata frame carries no audio, and every reference tool excludes it. (b) is rejected because the count must come from parsing frames — the Xing field is a cross-check, not the source.                                                                                                                                                                                                                                                                                   | [sample ground truth](docs/evidence/sample-ground-truth.html)                                |
| D2  | TypeScript pinned to 5.9.3.                                                                                                                                          | TypeScript 7.0.2, the current release.                                                                                                                       | `ts-jest` declares the peer range `typescript: ">=4.3 <7"`, so 7.x is not supported by the test toolchain. Newest is not the same as compatible.                                                                                                                                                                                                                                                                                                                                                                                                                  | `npm view ts-jest peerDependencies`                                                          |
| D3  | CommonJS modules.                                                                                                                                                    | ESM.                                                                                                                                                         | Jest on ESM still needs `--experimental-vm-modules`, and this service has no ESM-only dependency. The friction buys nothing here.                                                                                                                                                                                                                                                                                                                                                                                                                                 | —                                                                                            |
| D4  | Fastify with `@fastify/multipart`.                                                                                                                                   | Express with multer.                                                                                                                                         | Streaming multipart parts with byte limits are first-party in Fastify; multer's defaults buffer to memory or disk, which contradicts the requirement to handle large files without growing memory. Fastify's `inject()` also gives HTTP tests with no sockets.                                                                                                                                                                                                                                                                                                    | [architecture](docs/model/architecture.html)                                                 |
| D5  | Error bodies carry a `code` field alongside `statusCode`, `error` and `message`; unexpected 5xx errors are logged and returned without detail.                       | Plain Fastify `{ statusCode, error, message }`.                                                                                                              | `code` is native to Fastify — it serialises a thrown error's `code` automatically, and its own built-in errors (`FST_ERR_CTP_INVALID_MEDIA_TYPE`) already include one, so omitting ours would make the API less consistent, not simpler. It properly instruments the service: clients branch on a stable code rather than on prose. Fastify's default handler echoes the raw exception message on a 500, which leaks internals — a custom handler is required to suppress that.                                                                                   | Probed against Fastify 5.12.1; see the error table in [README](README.md)                    |
| D6  | `tsx` for the `dev` script.                                                                                                                                          | (a) `tsc --watch` plus `node --watch`. (b) `node --experimental-strip-types`. (c) No `dev` script.                                                           | Investing in developer convenience shortens the inner loop and so raises throughput. `tsx` is standard industry practice with wide community familiarity, not a bespoke in-house harness, so it costs little to adopt or explain. (a) needs two concurrent processes, which no npm script expresses portably across `cmd.exe` and POSIX shells; (b) requires Node 22.6+ and would raise the supported floor above the stated Node 20. Caveat: `tsx` transpiles without type checking, so `npm run verify` remains the gate.                                       | 3 packages added; `engines: node >=20`                                                       |
| D7  | Remove Fastify's built-in content-type parsers and add a catch-all that throws `UNSUPPORTED_MEDIA_TYPE`.                                                             | Keep the JSON and text parsers and test `request.isMultipart()` inside the route.                                                                            | This API accepts exactly one body format. Without it, a `application/json` body would be parsed and rejected in the route while an `application/xml` body would get Fastify's bare "Unsupported Media Type" — two paths, two messages, same status. The catch-all makes every non-multipart request produce one actionable message naming what was received.                                                                                                                                                                                                      | `test/http/fileUpload.test.ts`, the 415 cases                                                |
| D8  | `Config` is built in `src/config.ts` and passed into `buildApp()`.                                                                                                   | Import configuration directly wherever it is needed.                                                                                                         | Keeps environment access in one file and lets tests build an app with a different upload limit without mutating `process.env` — the 413 test sets a 1 KB limit this way. Invalid values throw at startup instead of silently reverting to a default.                                                                                                                                                                                                                                                                                                              | `src/config.ts`, `test/http/fileUpload.test.ts`                                              |
| D9  | `parseFrameHeader` returns `null` for anything that is not a valid MPEG-1 Layer III header, rather than throwing.                                                    | Throw a `NotAFrameHeaderError`; return a discriminated union `{ ok: true } \| { ok: false, reason }`.                                                        | Invalid bytes are the normal case, not an exceptional one: resynchronisation after damaged data tests one candidate offset per byte, so failure is the common path and must stay cheap and quiet. A reason code would only be surfaced during resync, where it is discarded.                                                                                                                                                                                                                                                                                      | `src/mp3/frameHeader.ts`, `test/mp3/frameHeader.test.ts`                                     |
| D10 | Free-format (bitrate index 0) and reserved (index 15) headers are rejected.                                                                                          | Accept free format and measure each frame's length by scanning to the next sync word.                                                                        | Free format does not declare its bitrate, so a frame's length cannot be derived from its own header — the only way to size it is to search for the next sync, which abandons the jump-by-length strategy the whole counter is built on for a format the assignment does not require. Rejecting it keeps every frame self-describing.                                                                                                                                                                                                                              | [mp3 structure](docs/concepts/mp3-structure.html)                                            |
| D11 | Where mediainfo and ffprobe disagree, follow ffprobe: exclude the metadata frame. `cbr-64-mono-info.mp3` is reported as 78, not mediainfo's 79.                      | Follow mediainfo unconditionally, since the assignment names it as the tool to verify against.                                                               | mediainfo is not self-consistent: it excludes the Xing frame on the VBR sample (6089 of 6090) but includes the Info frame on the CBR fixture (79 of 79), apparently reading the declared field for VBR and counting physically for CBR. ffprobe excludes it in both cases, and so does each file's own metadata field. Following the tool that contradicts itself would make the API's answer depend on the encoder's bitrate mode.                                                                                                                               | [ground truth](docs/evidence/sample-ground-truth.html), `test/fixtures/expected-counts.json` |
| D12 | Re-establishing sync requires two headers one frame apart; a frame whose declared length runs past the end of the audio is not counted.                              | Accept any single valid-looking header; count a truncated final frame.                                                                                       | An 11-bit sync word followed by plausible fields occurs readily in compressed payload and in unrelated binary files, so a lone header would give arbitrary files a non-zero frame count — which step 5 needs to report as an error, not a number. Requiring the pair costs one extra read per resync and nothing at all while in sync.                                                                                                                                                                                                                            | [counting frames](docs/concepts/frame-counting.html), `test/mp3/countFrames.test.ts`         |
| D13 | Ship the buffer counter behind the route first, then replace it with a streaming counter. The handler currently collects the upload into one buffer before counting. | Build the streaming counter first and wire the route once, at the end.                                                                                       | A correct endpoint that answers 6089 today is worth more than a perfect one that answers nothing yet, and it makes the remaining work a contained substitution: the counting rules, the response shape and the error shape are already fixed and tested, so only the memory profile changes. Peak memory is bounded by `MAX_UPLOAD_BYTES` in the meantime, which is a cap the service already enforces rather than a new exposure.                                                                                                                                | [architecture](docs/model/architecture.html)                                                 |
| D14 | Accept the MP3 either as a multipart file part or as the raw request body, and treat any non-multipart body as raw bytes whatever its `Content-Type` says.           | (a) Require `multipart/form-data`, rejecting anything else with 415. (b) Allowlist binary content types such as `audio/mpeg` and `application/octet-stream`. | The specification asks for "an MP3 file upload via the POST method" without naming a transfer format, so a client that posts the file directly is making a reasonable request. (b) fails the most likely test command: `curl --data-binary @sample.mp3` sends `application/x-www-form-urlencoded` unless told otherwise, so an allowlist rejects a perfectly good upload over a header the caller never chose. The bytes are authoritative — a body that is not MPEG-1 Layer III is reported as such, which is a more useful message than a media-type complaint. | `test/http/fileUpload.test.ts`, the raw-body cases                                           |
| D15 | Finding no frames is an error (400 `NO_FRAMES_FOUND`), not a successful count of zero.                                                                               | Return `{ "frameCount": 0 }`.                                                                                                                                | Zero would claim the file is a valid MP3 that happens to contain no audio, when the real cause is almost always a file of another kind. Returning 200 for a JPEG is a wrong answer dressed as a right one. This is also what makes accepting any `Content-Type` safe: the check that used to live in a media-type guard now lives where the evidence actually is.                                                                                                                                                                                                 | `test/http/fileUpload.test.ts`, the not-an-MP3 cases                                         |
| D16 | Count frames incrementally as chunks arrive, and have the whole-buffer helper delegate to the same class rather than keeping a second implementation.                | (a) Keep the buffer counter and rely on the upload limit to bound memory. (b) Write a separate streaming counter alongside the buffer one.                   | A frame is decided entirely by its own four-byte header, so nothing earlier in the file is needed and the reader can carry a fixed amount of state: at most one frame while it looks for the start of the stream, plus the trailing 128 bytes that may be an ID3v1 tag. Measured heap growth was 3.9 MB over 208.6 MB of input. (b) was rejected because two implementations of the same rules drift; delegating means the existing counter tests exercise the streaming machine, and chunk-size invariance is the only thing left to test separately.            | [measurements](docs/evidence/streaming-memory.html), `test/mp3/frameCounter.test.ts`         |
