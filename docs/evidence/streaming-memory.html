Streaming counter measurements

Memory, throughput and chunk-size behaviour of the incremental counter; informs src/mp3/frameCounter.ts and the upload route.

The answer does not depend on chunk size

test/fixtures/sample.mp3 fed through one counter in fixed-size pieces. A one-byte chunk splits every header across four calls; 7 and 100 divide frames at offsets that never align with a boundary.

Chunk size (bytes) 1 7 100 4096 whole file
Frames 6089 6089 6089 6089 6089
Bytes resynchronised 0 0 0 0 0
Time 246 ms 39 ms 2 ms 1 ms < 1 ms

Memory does not grow with the stream

The same input fed to both counter designs, in 64 KB chunks, on the same machine. Node keeps Buffers outside the V8 heap, so heapUsed alone would miss exactly the allocation that separates them; the figures below are heapUsed + arrayBuffers, sampled every 5 ms, each the middle of three runs. npm run bench reproduces this table and the one above.

Input v1 buffered — peak growth v2 streaming — peak growth
104.3 MB 108.4 MB 2.2 MB
208.6 MB 212.7 MB 4.9 MB
417.2 MB 425.5 MB 13.9 MB

The buffered counter needs slightly more than the input, because holding the file is what it does. The streaming counter never exceeds a few per cent of it. What that counter actually retains is about a kilobyte — a partial header, a position, and 128 withheld bytes — so the megabytes that do appear are arriving chunks waiting to be collected rather than anything it is keeping. Both designs return identical counts throughout.

The streaming counter retains only what it cannot yet decide: at most one frame while it is looking for the start of the stream, and the trailing 128 bytes that may prove to be an ID3v1 tag. The largest MPEG-1 Layer III frame is 1045 bytes, so the ceiling is on the order of a kilobyte whatever the file size.

The same holds through the HTTP layer

A 146 MB file — 105 copies of the sample concatenated, so 105 × 6090 − 1 frames, since only the first copy's Xing frame opens the stream — uploaded to a running server.

Upload Response Wall clock Server resident memory
— — — 70.3 MB at rest
146 MB, multipart {"frameCount":639449} 0.69 s 73.2 MB
146 MB, raw body {"frameCount":639449} 0.84 s 77.8 MB

Two uploads totalling 292 MB moved resident memory by 7.5 MB, none of it proportional to the files. Throughput is roughly 200 MB/s, so the request is bounded by the network rather than by the parsing.

The size limit is enforced without buffering

With MAX_UPLOAD_BYTES=5000000, the same 146 MB file on both paths:

Path Result
Raw body 413 FILE_TOO_LARGE, refused once the limit was passed
Multipart 413 FILE_TOO_LARGE, identical body

Neither request stalled and the server answered a normal upload immediately afterwards, which is the failure mode worth checking: rejecting a request part-way through its body leaves the connection to be torn down correctly.

Many uploads at once

Flat memory per request is only half of scalability; the other half is what happens when several arrive together. Each batch below was fired simultaneously at one server process, with resident memory sampled throughout.

Batch Data in flight All counts correct Wall clock Aggregate Peak resident memory
50 × 1.4 MB 70 MB yes 152 ms 456 MB/s 103 MB
200 × 1.4 MB 278 MB yes 438 ms 635 MB/s 123 MB
8 × 146 MB 1168 MB yes 1431 ms 816 MB/s 99 MB

The last row is the one that matters. Over a gigabyte of upload data was in flight at once and the process never passed 99 MB, because no request ever holds its own file. The buffered design would have needed room for all eight at the same time. Throughput rises with concurrency rather than falling, since one request's counting overlaps another's network wait.

The server answered a normal upload immediately after each batch and logged no errors. Node runs this work on one thread, so the ceiling is CPU rather than memory: past roughly 800 MB/s of counting, further concurrency adds latency instead of throughput. Nothing here limits the number of simultaneous uploads — a real deployment would want one, and it is named in the README's future work.
