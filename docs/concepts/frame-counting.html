Counting frames

The rules that decide what counts as a frame — which bytes are audio, which are metadata, and what to do with damage. How those rules are applied to a stream arriving in pieces is a separate matter, covered in counting as bytes arrive. Informs src/mp3/frameCounter.ts.

The walk

Frames are located by arithmetic, not by searching. Each header declares its own length, so the next header is expected exactly that many bytes later. Scanning happens only to recover after that expectation fails, which makes the common case one read per frame rather than one per byte.

Rules

Situation Rule Why
Leading ID3v2 tag Skip 10 + syncsafe size (plus 10 more if the footer flag is set) Tag bodies contain arbitrary bytes, including 0xFF runs that scan as sync words
Trailing ID3v1 tag Treat the file as ending 128 bytes early The tag is not audio and must not be scanned as frames
The first frame of the stream is Xing / Info / VBRI Tally it separately; do not include it in frameCount It carries encoder metadata, not sound — decisions.md D1 and D11
Header invalid at the expected offset Advance one byte and look again, marking the stream out of sync A frame boundary can land anywhere after damage, so every offset is a candidate
Out of sync Require a second header exactly one frame later before accepting the first A lone sync word occurs readily in ordinary binary data; two that agree do not
Out of sync, and the candidate ends exactly at the end of the stream Accept it — there is no second header, and there never will be Otherwise a file holding a single frame would be reported as holding none
Final frame runs past the end Do not count it Its audio is not in the file; counting it would overstate the content

Why one sync word is not enough

A header begins with eleven set bits, but that pattern appears often in compressed audio payload and in unrelated binary files. Accepting it alone would report a frame count for a JPEG. The counter therefore trusts a candidate only once a second header sits exactly where the first one's declared length says it should — a coincidence that arbitrary data almost never produces. Once the chain is established each link is trusted on its own, so the check costs nothing on an undamaged file.

There is exactly one place the rule relaxes. If the stream ends and the candidate's declared length lands precisely on the last byte, no confirming header can ever arrive, so the candidate is accepted. Without that, a file containing a single frame would be reported as containing none. The cost is that four bytes of arbitrary data could be counted as one frame if they happen to parse as a header and declare a length reaching exactly the end of the file — a coincidence that has to hold to the byte, and which at worst is off by one.

This is worth being clear about, because damaged MP3s are rare and nothing in this service's requirements asks for them. The rule is not there to salvage broken files. It is there because rejecting something that is not an MP3 and recovering from damage are the same problem: both are a matter of never assuming that the next bytes are a frame. The same rule also finds the first frame of a perfectly good file, since the counter begins every stream out of sync, and it walks quietly past legal structures this parser does not know — an APEv2 tag at the end of a file, or padding left by a tagger — instead of failing on them.
