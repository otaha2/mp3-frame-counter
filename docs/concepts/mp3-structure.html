MPEG-1 Layer III file structure

What an MP3 file is made of, and what the four bytes at the start of every frame mean; informs src/mp3/frameHeader.ts.

What a frame is

An MP3 is not one continuous recording. It is a long run of small, independent packets called frames, each holding a fixed 1152 samples of audio — about 26 milliseconds at CD sampling rates. A three-minute track is roughly seven thousand of them, end to end.

Every frame opens with four bytes describing how that frame was encoded, and those four bytes are the whole reason frames can be counted without understanding audio: they give the frame's length, so the next frame's position is calculated rather than searched for.

Two terms recur below. Bitrate is how much data each second of audio was given; a higher bitrate means larger frames. An encoder may use one bitrate throughout (constant bitrate, CBR) or vary it to spend more data on complicated passages (variable bitrate, VBR). Both appear in this project's fixtures, and the counter treats them the same way because every frame declares its own size.

File anatomy

Those frames are optionally wrapped in metadata tags, which hold no audio and are not frames: 

[ID3v2 tag?] [frame][frame][frame] ... [frame] [ID3v1 tag?]
  • ID3v2 (start, optional): 10-byte header "ID3" ver(2) flags(1) size(4). The size is syncsafe — 4 bytes of 7 bits each ((b6<<21)|(b7<<14)|(b8<<7)|b9), covering the tag body after the 10-byte header. Seven-bit packing keeps the size field itself from ever holding 0xFF and being misread as a frame start. The body has no such protection and often contains 0xFF runs inside album art, which is why the tag is skipped by its declared size and never scanned.
  • ID3v1 (end, optional): exactly 128 bytes beginning "TAG" at EOF−128. Contains no frames.
  • Xing/Info/VBRI frame (optional): the first frame after ID3v2 may be a metadata frame — structurally a real frame, but carrying a summary of the file written by the encoder instead of audio. LAME, the most widely used MP3 encoder, writes "Xing" into a variable-bitrate file and "Info" into a constant-bitrate one. The marker sits 36 bytes into the frame for MPEG-1 stereo: past the 4-byte header and 32 bytes of side information, a block describing how that frame's audio was packed. A mono frame has only one channel to describe, so its side information is 17 bytes and the marker sits at offset 21 — the reader must know the channel mode before it knows where to look. "VBRI" is a rarer variant, always at offset 36. Its stored frame and byte counts describe the rest of the stream. Counting policy: see decisions.md D1.

The four-byte header

The fields are packed into 32 bits, most significant first. The letters are the labels the MPEG specification uses, so other references can be read alongside this table.

Bits Size Field Accepted values (this project)
A 31–21 11 Sync word all 1s (0x7FF)
B 20–19 2 MPEG version 11 = MPEG-1 only; 10 is MPEG-2, out of scope
C 18–17 2 Layer 01 = Layer III only
D 16 1 CRC protection either; 0 puts a two-byte checksum after the header
E 15–12 4 Bitrate index 1–14 → 32…320 kbps; 0000 (free) and 1111 rejected
F 11–10 2 Sampling rate index 00=44100, 01=48000, 10=32000; 11 rejected
G 9 1 Padding 0 or 1 — adds one byte to this frame only
H 8–0 9 Private, channel mode, mode extension, copyright, original, emphasis any; only the channel mode is read, and only to locate a Xing marker

In bytes, a header opens with 0xFF followed by a byte whose top three bits are set — which is why real files are full of FF FB and FF FA. Searching for that pattern is how a reader finds its place, but this counter only searches when it has lost it: while in sync it steps to the next header by arithmetic, which is both faster and far less prone to false positives.

The CRC is worth being careful about. When bit D is 0 a two-byte checksum follows the header, but the frame does not become two bytes longer — the checksum takes space that would otherwise hold audio. Frame length is decided by bitrate, sampling rate and padding alone, which is why this parser can ignore the CRC entirely.

MPEG-1 Layer III bitrate table (index → kbps): 1→32, 2→40, 3→48, 4→56, 5→64, 6→80, 7→96, 8→112, 9→128, 10→160, 11→192, 12→224, 13→256, 14→320.

Frame length — how the walk works

Every MPEG-1 Layer III frame carries 1152 samples, so its byte length is fully determined by its own header: 

frameLength = floor(144 × bitrate / sampleRate) + padding

(144 = 1152 samples ÷ 8 bits.) The counter never scans for the next sync — it jumps by the computed length and expects a valid header at the landing offset. A scan is only used to resync after an invalid header.

One header, decoded

The four bytes at offset 44 of test/fixtures/sample.mp3 are FF FB 50 00. Written out in bits, with each field marked by its letter from the table above: 

    FF         FB         50         00
 1111 1111  1111 1011  0101 0000  0000 0000
 AAAA AAAA  AAAB BCCD  EEEE FFGH  IIJJ KLMN
Field Bits Value Meaning
A — sync 111 1111 1111 0x7FF All eleven set. This is where a frame may begin.
B — version 11 3 MPEG-1. Anything else is refused.
C — layer 01 1 Layer III. Anything else is refused.
D — CRC 1 — Not protected, so no checksum follows. Either value is accepted.
E — bitrate 0101 5 Index 5 in the table above → 64 kbps.
F — sampling rate 00 0 44100 Hz.
G — padding 0 0 No extra byte on this frame.
H–N 0 0000 0000 — Private bit, then channel mode 00 = stereo, then flags this parser does not read.

So the frame is 208 bytes long: floor(144 × 64000 / 44100) + 0 = floor(208.9…) = 208. The next header must therefore begin at offset 44 + 208 = 252 — and it does, which is the whole of the walk.

Two details of this particular frame are worth noticing. Its channel mode says stereo, while every audio frame in the file says joint stereo: it is the Xing frame, and the encoder wrote it with different settings from the audio it describes. And at 64 kbps it is much larger than the 32 kbps frames that follow it — the metadata frame is sized to hold its table, not its (absent) audio.
