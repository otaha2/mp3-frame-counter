Counting as bytes arrive

A walkthrough of how the counter works when the file is delivered in pieces; explains src/mp3/frameCounter.ts line by line in plain terms.

The one idea everything rests on

Every frame starts with a four-byte label. That label says, among other things, how long the frame is. So once you know where one frame begins, you know exactly where the next one begins — you never have to look at the audio in between.

Counting frames is therefore not a search. It is a walk: read a label, step over that many bytes, read the next label, step again. The audio itself is never examined. 

[label: 208 bytes] ................................. [label: 104 bytes] ...........
 ^                                                   ^
 read here, then step 208 bytes                      the next label is exactly here

What makes it awkward

The file arrives over a network in pieces of whatever size the network felt like. A piece may end in the middle of a label, so only two of its four bytes have turned up. A single frame may be spread over dozens of pieces. The counter has to survive being interrupted anywhere, and it must not solve the problem by keeping the file — that would defeat the point.

So it keeps two things, and only two:

pending The handful of bytes that have arrived but cannot be decided about yet.
skipRemaining How many bytes of the current frame are still to be walked past.

That second one is the trick. If a frame is 417 bytes and a piece only covers 20 of them, the counter walks past those 20, writes down “397 to go”, and throws the bytes away. It does not need them. It already knows what they are: the middle of a frame.

Three things the counter can be doing

There is a fourth possibility that is not really a state: waiting. If fewer than four bytes have arrived, no label can be read, so the counter stops and returns. The next piece of the file will carry on from exactly where it left off.

Watching it work: a clean file in 100-byte pieces

This is the real sample file, fed in through 100 bytes at a time. Its first frame begins at byte 44, after an ID3v2 tag, and is 208 bytes long. The second is 104 bytes.

Bytes in so far What happens
100 Nothing yet — see “the last 128 bytes” below.
200 The tag says it is 44 bytes long, so walk past 44. At byte 44 a label appears saying “208 bytes”. Not enough of the file has arrived to check it. Wait.
300 Still not enough to check the label. Wait.
400 Now byte 252 has arrived, and there is a second label sitting there — exactly where the first one said it would be. Both are believed. Walk past 208 bytes: frame 1 complete. Read the label at 252, which says 104, and walk past the 20 bytes of it that have arrived. 84 to go.
500 Walk past the remaining 84: frame 2 complete. Read the next label, walk past 16 of its 104 bytes. 88 to go.
600 Walk past 88: frame 3 complete. And so on, 6089 times.

Notice what never happened: no byte was ever looked at twice, and nothing was stored except a countdown and a few undecided bytes.

Watching it recover: a file with damage in the middle

Four frames of 417 bytes each, with 35 bytes of rubbish injected after the second one.

Position What happens
0 Label says 417. Walk past it. Frame 1 complete.
417 Label says 417. Walk past it. Frame 2 complete.
834 A label was expected here and there is none. Lost. Try byte 835, then 836, then 837 — one at a time, 35 times.
869 A label appears. Because the counter is lost, one label is not enough: it checks that a second label sits 417 bytes further on. It does. Trust restored, frame 3 complete.
1286 Back to walking. Frame 4 complete.

The final answer is 4 frames and 35 bytes discarded — exactly the rubbish that was inserted. The damage cost nothing but the bytes it occupied.

Why one label is not enough when lost

A label begins with eleven bits that are all 1s. That pattern is common: it appears inside compressed audio, inside photographs, inside almost any large file. If the counter believed every plausible label it found, it would report a frame count for a JPEG, and the API would answer a confident number for a file that is not music at all.

So while it is lost, the counter demands a second opinion: a label must be followed by another label at precisely the distance the first one claimed. Two accidents agreeing to the byte is vanishingly unlikely. Once the chain is running the check is dropped, because the chain is itself the evidence — which is why this costs nothing on an undamaged file.

Why the last 128 bytes are held back

Some MP3 files end with a 128-byte block of text: the track title, artist, year. It is not audio and must not be counted. The trouble is that you cannot tell you are at the end of a stream until it ends — and by then you have already read the bytes.

So the counter always keeps the most recent 128 bytes unexamined, staying deliberately a little behind. When the stream finishes, it looks at those held-back bytes: if they are a tag, it discards them; if they are audio, it counts them. This is why nothing happened in the example above until 200 bytes had arrived — the first 100 were still inside the withheld window.

Everything the counter remembers

This is the complete state. It does not grow, no matter how large the file is.
