Questions and answers

A guided path through how this service counts frames: the idea it rests on, the cases that complicate it, and how the numbers were checked.

Why this page exists

It was written while learning the format, not afterwards. The questions that follow are the ones that actually blocked progress, in the order they blocked it, and the answers are what unblocked them — which is why several are about tools disagreeing rather than about code. Keeping them turns a private struggle into something reusable.

Two kinds of reader are expected. Someone who only wants to know what the service does can stop after the first three answers and be correctly informed. Someone about to change the code should follow the links: each answer is deliberately one screen, with the depth kept in the knowledge log and the reasoning in decisions.md, so the choice of how far to go stays with the reader rather than being made for them.

How it works

How are the frames counted?

An MP3 is a sequence of frames, and every frame opens with a four-byte header that declares the bitrate and sampling rate it was encoded at. Those two numbers give the frame's length in bytes. Counting is therefore a walk rather than a search: read a header, step forward by exactly that many bytes, and the next header is waiting there. The audio itself is never decoded or even examined — only the headers are read.

The file format, field by field →

Where does one frame end and the next begin?

The header alone decides it: length = floor(144 × bitrate ÷ sampleRate) + padding. A frame always carries 1152 samples, so its size follows from how fast it was encoded; 144 is 1152 samples divided by 8 bits per byte. The padding bit adds a single byte, which is how an encoder absorbs the remainder when that division is not exact. On the provided sample this walk lands on a valid header 6090 times in a row and finishes on the file's last byte, with nothing left over.

An MP3 carries metadata at both ends. Is any of it counted?

None of it, and each kind is excluded differently. An ID3v2 tag sits at the front and declares its own size, so it is skipped by arithmetic — that size field is stored seven bits per byte precisely so nothing inside a tag can be mistaken for a frame header. An ID3v1 tag is exactly 128 bytes at the very end, so the last 128 bytes are held back until the stream finishes and only then examined. A third kind hides in plain sight: the first frame may be a Xing or Info frame, structurally a real frame but carrying encoder statistics instead of sound. It counts as structure rather than audio, which is the difference between the 6090 frames in the sample and the 6089 reported for it.

What happens to a damaged file, or one that is not an MP3 at all?

When a header is not where the previous frame said it would be, the counter moves forward one byte at a time until it finds one. Trust is then re-established only by two headers, not one: a candidate is believed when a second header sits exactly one frame length further on. A single plausible header proves little, because eleven consecutive 1-bits occur readily inside compressed audio and inside unrelated files — without that second opinion a photograph would appear to contain frames. That is the real reason the rule exists: damaged MP3s are rare, but telling an MP3 from anything else is the same problem, and the same check does both. A file with no frames at all is answered with a 400 naming the format that is supported, rather than a cheerful count of zero.

Why one sync word is not enough →

Why is the upload counted as it arrives instead of being read first?

Because nothing about counting needs the whole file. A frame is decided entirely by its own four-byte header, so the reader carries a fixed amount of state — a partial header split across two chunks, and how far it is into the current frame — and discards everything else as it goes. Peak memory stays under 4 MB whether 104 MB or 417 MB is counted, where the earlier design that buffered the file needed room for all of it. The same holds across requests: eight simultaneous 146 MB uploads put over a gigabyte in flight and never took the server past 99 MB. The configured size limit therefore bounds how large a request may be, not how much memory one costs.

How is the count known to be correct?

Every count is checked against tools written by other people. mediainfo and ffprobe both report 6089 for the provided sample, and the file's own Xing header declares 6089 as well. Three short files were generated with ffmpeg to cover shapes the sample does not — constant bitrate, a single channel, an ID3v1 tail — and their counts live in test/fixtures/expected-counts.json, which is treated as ground truth and never edited to make a test pass. A fourth witness appeared by accident: of the 6090 frames in the sample, exactly one declares stereo and 6089 declare joint stereo, and the odd one out is the metadata frame.

Every measurement taken →

Why does this count differ from mediainfo on one of the files?

On a constant-bitrate fixture mediainfo reports 79 while ffprobe reports 78. The file holds 79 structurally valid frames, the first of which is an Info metadata frame whose own count field reads 78. The two tools are not measuring the same thing: for a variable-bitrate file mediainfo appears to repeat the count declared in the header, while for a constant-bitrate one it counts frames itself — so its answers are not consistent with each other across the two files.

A truncated file makes the difference plain. Cut the sample to 20000 bytes and mediainfo still reports 6089, a number describing a file that no longer exists, while ffprobe reports 96, counting a final frame missing 234 of its 261 bytes. This service reports 95: the frames whose bytes are all present, less the metadata frame. Matching the tool that contradicts itself would make the answer depend on how the file happened to be encoded.

The decision, with the alternatives →

What is deliberately not handled?

MPEG Version 2 and 2.5 and Layers I and II are out of scope, and are rejected with a message naming the format that is supported — handled deliberately rather than by accident. Free-format files are rejected for a sharper reason: they do not declare a bitrate, so a frame's length cannot be derived from its own header and the jump-by-length approach does not apply to them at all. A request carrying more than one file is not supported either: the first file is read, and the only promise made is that a caller's mistake is never reported as a server error. Each of these is named in the README alongside what happens instead.

4. While the upload is still arriving, why are the last 128 bytes held back?
  1. To leave room for a checksum.
  2. Because an ID3v1 tag is exactly that long, and a byte cannot be known to be in the final 128 until the stream stops.
  3. To align reads onto a block boundary.
Answer

b — so the counter stays deliberately 128 bytes behind, and decides what those bytes were once the upload ends.

5. After damage, why is a single valid-looking header not enough to resume counting?
  1. The specification requires headers to appear in pairs.
  2. The first header after damage is always corrupt.
  3. Eleven consecutive 1-bits occur by chance in ordinary data, so a second header at the declared distance is needed to confirm it.
Answer

c — two accidents agreeing to the byte are vanishingly unlikely, while one on its own is common enough that a photograph would appear to contain frames.
