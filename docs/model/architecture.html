Architecture

Covers the layering of the service and the path a request takes through it; informs everything under src/.

Layers

Two layers with a one-way dependency. The domain never learns that HTTP exists, so it can be unit-tested with byte arrays and reused outside a server.

Request path

How the upload is read

A multipart upload reaches the route as a readable stream of parts, with a byte limit applied by busboy so an oversized file is refused at the limit rather than after the whole body has arrived. A part must be read to its end even when its bytes are not needed: busboy will not finish parsing the request, and the response will not be sent, while a part stream is still pending. A raw body is left unparsed and read straight from the request instead, with the same limit applied as its bytes are counted.

What happens to those chunks is the difference between the two counter designs below. Both return the same number for the same bytes; they differ in what has to be held in memory while doing so.

v1 — buffer counter (superseded)

Chunks were collected until the upload ended, joined into one buffer, and counted in a single pass. The counter could index freely into the whole file, which made the walk and the resynchronisation logic straightforward to write and to test — at the cost of holding the upload in memory. countFrames survives as a convenience for callers that already hold the bytes, but it delegates to the streaming counter, so there is one implementation of the rules rather than two that can drift.

v2 — streaming counter (current)

Each chunk is counted as it arrives. A frame is decided entirely by its own four-byte header, so nothing earlier in the file is needed and a frame spanning several chunks is skipped by arithmetic rather than assembled. What survives between chunks is fixed in size: a header split across a boundary, how far into the current frame the reader is, and the trailing 128 bytes that may turn out to be an ID3v1 tag. Counting 417 MB peaks at 13.9 MB where buffering the same input needs 425 MB, and eight simultaneous 146 MB uploads — over a gigabyte in flight — never took the server past 99 MB. See the measurements.

v1 — buffer v2 — streaming
Peak memory per request Size of the upload, capped by MAX_UPLOAD_BYTES About a kilobyte, whatever the file size
Concurrent large uploads Each holds its own buffer; 10 at once is ~2 GiB Cost is the same as one
Count available After the last byte arrives Continuously; final on the last byte
Counting rules Identical — same headers, same resynchronisation, same result

Current state

Both upload paths count incrementally. The endpoint answers with a count verified against mediainfo for every file in test/fixtures/, and the answer is unchanged whether the bytes arrive one at a time or all at once. Rationale for each choice is in decisions.md.
